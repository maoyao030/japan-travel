# 住宿頁的自動寫作流程（2026-11-19）

排定工作 `japan-travel-daily-writer` 挑到住宿頁（大綱裡主題是住宿的頁，包含主頁與有 `parentArticleId` 的專門頁）時，不照 `local-writer.md` 第 2～4 步，改照這份文件做，做完接 `local-writer.md` 第 5 步上傳。

這套流程是 2026-11-18～19 人工 session 把六篇舊住宿主頁、富良野滑雪住宿與旭川三頁專門頁重跑一輪時用的，Darren 看過十頁後說「飯店都沒問題了，住宿就這樣吧」。寫法的規則在寫作 Skill，這份文件只管順序、派誰做、卡住時怎麼辦。

- 寫法：`.agents/skills/japan-travel-answer-first/references/core-style.md`（每一頁都一樣的寫法，分段作者與編輯先讀）、`stay-page.md`（主頁）、`stay-topic-page.md`（專門頁；最後一節「住客怎麼說」主頁也適用）、`sentence-rhythm.md`。
- 做過的十頁可以當前例：封包在 `content-production/<id>/`，研究與每一步的紀錄在 `content-experiments/stay-rerun-2026-11-18/<地點>/`；學到的事在同資料夾的 `RUNBOOK.md`。
- 住宿頁不受「先有頁型範本」限制（`local-writer.md` 第 1 步那一條）：格式 Darren 已經認可。

## 模型與角色

| 角色 | 模型 | 備註 |
|---|---|---|
| 分段作者 | Sonnet 5.5（Agent 工具 `model: sonnet`） | 一段一位 |
| 研究、規格、分段編輯、接縫、事實查核、讀者驗收、找貼文 | Opus 5.5（`model: opus`） | 查核與驗收不能是作者或編輯 |
| 協調者（這個 session） | 不寫正文 | 只組稿、跑程式、照查核者給的改法改字 |

這張表只限住宿頁（Darren 2026-11-16）；其他頁型仍照 `local-writer.md` 只用 Opus 4.6。協調者不得自己把查核紀錄 `fact-check.json` 改成通過；每次改稿後都要請原本那位查核者確認並更新雜湊。

## 步驟

每一步的產出放在 `content-experiments/stay-auto/<id>/`（研究與草稿）與 `content-production/<id>/`（封包）。子代理一律等它完整回傳、親自確認檔案存在才做下一步。

1. **問法與官方研究**（一位）：中文與日文 Google 自動完成（用 python urllib，Git Bash 的 curl 會弄壞中日文）；逐間到官網查位置、接送、溫泉、餐、房型、營業期間、訂房管道、設施費用。產出 `queries.md`、`facts.md`（K 編號、網址、查核日、原文短句）、`coverage.md`（哪些頁要用瀏覽器、哪幾間要讀評論）。
2. **瀏覽器研究**（一位，查核角色）：讀讀取工具讀不到的官方頁與訂房日曆；讀住客評論（Trip.com 列得出來的最多 3 頁、4travel 第 1 頁、Google 地圖不登入看得到的 5 則）；查 Trip.com、Agoda 上架與能不能訂。產出 `facts-extra.md`、`facts-reviews.md`、`booking-links.md`。
   - **評論一個點記一筆**：飯店、主題、這個點、正面或負面、各平台則數、日期範圍、可用與否（兩個平台以上、合計三則以上）、備註（和官網衝突、舊評論、反面說法各幾則）。不存評論原文與照片。
   - 只手動讀、不用程式抓；不登入任何帳號；遇到驗證碼或登入牆就停那個網站；同一時間只有一位助手用瀏覽器。
   - **這一輪沒有瀏覽器工具可用時**：這篇記進執行紀錄「停放：等瀏覽器讀評論」，換下一篇不是住宿頁的文章；不要跳過評論直接寫。
3. **規格與動筆前檢查**（一位）：`page-spec.md`（H1 用「○○住宿推薦，住 A 還是 B？」這種讀者最先要決定的事；每節的標題、要回答的問題、用哪些事實、字數；細寫 5～6 間的賣點與限制；比較表每格的事實；內連句）、`WRITE.md`（拆 4～5 段）、`EDIT.md`。動筆前檢查有缺口就回第 1、2 步補，補不到的照下面「預設做法」處理。
4. **分段寫作**（每段一位作者）→ **分段編輯**（每段一位，逐句對事實、刪規格與廢話、賣點要具體）。
5. **組稿、接縫、句子節奏、份量檢查**（一位）：補 H1、資料來源與最後一行「資料更新：○年○月」；同一件事只在一處講細節；每間正文 180～300 字（加了「住客怎麼說」後上限 480 字）；太少退回作者、太多退回編輯。
6. **住客怎麼說**（併在第 5 步或另派一位）：照 `stay-topic-page.md` 最後一節。重點：
   - 每間一個 `**住客怎麼說**：` 條列小段，一點一條，不寫「有人說」這類字眼，強度照紀錄（少數、部分、大多、兩極）。
   - **只留**官網或上面介紹沒寫的事、最受好評的那一項、評價兩極或缺點；重複介紹再加「有好評」的、只有評價沒有內容的不留；篩完一條不剩就不放小段。
   - 每一個點各自達門檻才寫；不寫成本站的建議（「最好…」「值得…」）。
7. **程式檢查**：`check-voice.mjs --final`、`audit_answer_first.py --json`、`check-benchmark.mjs --after=`、`scripts/check-stay-topic.mjs`（主頁上「條列多間的 H3 沒有訂房行」這類專門頁才有的規定可以不理，其他錯誤要修）。
8. **事實查核 ∥ 讀者驗收**（各一位，同時派）：查核照 `japan-travel-acceptance` 的契約寫 `fact-check.json`，官方頁今天重開；驗收照七題寫 `acceptance<N>.md`。不過關就照他們給的改法改，改完請同一位確認。驗收最多退四次，四次還不過就停放。
9. **封包**：`publication.json`、`heading-review.json`、`review.md`（照前例格式，「協調者的決定」要寫清楚每個預設做法）、大綱與清單裡的標題同步；`node scripts/local-article-gates.mjs <id>` 要是 `gates_clear`。
10. **Instagram 貼文**（一位，用瀏覽器）：每間細寫的旅館找 1 則，寫 `images/embed-plan.json`（`pageType` 主頁填 `stay`、專門頁填 `stay-topic`）。Google 搜尋要寫 `site:www.instagram.com`。太舊、和現況打架、畫面印著價格、業配的不放；找不到就不放，不因此停放。
11. 接 `local-writer.md` 第 5 步上傳（封面、Sanity、CI、開放索引、D1），再放貼文。

## 預設做法（不用問 Darren）

| 情況 | 做法 |
|---|---|
| 住客說法達不到門檻、只靠舊評論、和官網衝突 | 不寫 |
| 巴士、渡輪時間和飯店交通頁對不上 | 照經營者的時刻表 |
| 只出現在擋讀取工具的訂房頁上的賣點，查核者重開不了 | 拿掉，資料來源也不放那個網址 |
| 營業期間、冬天開不開沒有官方來源 | 不寫成有開或休館；比較表寫「—」，需要時寫「出發前先向旅館確認」 |
| 只查到一季的日期 | 標年份 |
| 平台查不到任何可訂的日子 | 訂房行不放那個平台 |
| 有人搜、但官網打不開的旅館 | 不開小節，用一句好壞都有的住客說法加訂房連結 |
| 舊官網網域被別人拿走 | 整間不寫，網址不出現在任何地方 |
| 開頭想寫「推薦 N 間」 | 不寫數不出來的間數，改在第一個 H2 點名 |
| 封面找不到合格實拍 | 照 `local-writer.md`：不上傳，記進上傳停放 |

## 要停下來留給 Darren 的事

- 驗收退四次仍不過。
- 要改已上線的別頁才說得通（分工衝突）。
- 新的頁型或這份文件沒寫到的版面。
- 封面只能用 AI 圖。

這些記進執行紀錄的停放表與 `content-automation/unattended-summary.md`，不自己決定。

## 每篇做完

在 `content-automation/unattended-summary.md` 加一段：網址、H1、查核與驗收各幾輪、照預設做了哪些決定、之後要重查的日期。Darren 事後看這份摘要。
