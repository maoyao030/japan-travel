# 自動化評估：routine 能做到哪裡、怎麼運作才能放心交出去（2026-10-16）

給 Darren 看，也給之後設計自動發布流程的 session 讀。這份是建議，不是已經做好的東西；第六節列的設定要不要改，由 Darren 決定。

## 結論

- **可以交給 routine 的**：照已核准的大綱寫文章、查證、驗收、發布到 Sanity、回頭補內連、記錄每一輪的結果。這些都有規則和檢查程式可以擋錯，不需要你逐篇看。
- **不能交出去的**：選地區、核准每一群的大綱、抽查、聯盟帳號與平台規則、決定規則要不要改。照這個設計，你大約一到兩週看一次大綱，每週花半小時看摘要與抽查（估計值，要跑過第一群才知道）。
- **最難的不是寫單篇，是讓一群頁面互相對得上**：同一件事不在兩頁寫出兩種說法、連結不斷、班表換季時一起更新。解法是把「串接」放在大綱階段就決定好，並讓同一個地點的頁面共用一份事實表，而不是每篇寫的時候各自判斷。
- **放手要分三段**：先只跑到「驗收通過」不發布，再發布但不開放搜尋，最後才全自動。每一段有明確的過關條件（第五節）。
- 目前設定的每 3 小時一篇、每天 8 篇，對照禮文島試寫的實際成本偏快（第六節）。

## 二、建議的運作方式：三個迴圈

把工作拆成三個頻率不同的迴圈。你只出現在第一個迴圈的最後一步，其餘交給 routine。

### 迴圈 1：規劃（一群一次，你看一次）

1. 你選地區。
2. 找地點與主題、分成旅行群、產生頁面清單（選題 Skill）。
3. 每個地點做一份共用事實表。
4. 產出整群大綱，大綱檢查程式通過。
5. **你核准整群**。核准的內容寫進文章清單，就是 routine 的工作授權。

### 迴圈 2：生產（routine，每輪一篇）

每一輪：

1. 拿執行鎖；確認這一輪有時間上限，超過就停在安全的步驟並記錄。
2. 挑下一篇：已核准的群裡，照大綱的寫作順序，挑第一篇「還沒發布、沒有被停放、來源沒有過期」的頁面。
3. 照大綱與共用事實表寫作、標編號、分段檢查、標題檢查。
4. 四層驗收。
5. 結果分三種：
   - **通過**：發布到 Sanity，再回頭把舊頁裡指向這篇的連結句加上連結，跑網站檢查。
   - **事實錯誤**：自動修一次、重跑驗收。第二次還是不過就停放。
   - **架構問題**（缺事實、分工不對、大綱和實際資料對不上）：直接停放，標記「要回大綱」，不自己改分工。
6. 來源網站打不開：這篇延後、改寫下一篇；連續三天打不開才停放。
7. 寫執行紀錄，放鎖。

「停放」是新的狀態：這篇不會再被自動挑中，直到你或之後的 session 處理。沒有這個狀態，一篇過不了的文章會在每一輪被重挑，整條清單卡住。

### 迴圈 3：維護（每週與換季）

- **每週**：整理停放清單、待補內連清單、即將到期的事實，寫成一份摘要給你。
- **換季**：班表每年 4 月底與 10 月更換。共用事實表的每一筆交通事實記下適用期間，到期前把用到這筆事實的頁面排進重查。
- **每年**：住宿頁照 `nextReviewDue` 重查官網。
- **上線 90 天**：看 Search Console，產出建議（補必答問題、改標題），由你決定要不要做。

## 三、最難的部分：頁面與地點之間怎麼串

### 為什麼難

- 同一群的頁面是在不同時間寫的。寫禮文島交通時，渡輪訂票教學頁可能還沒上線，連結不知道要不要放。
- 同一件事很容易在兩頁各寫一次，而且說法不同。例如主頁寫「渡輪約兩小時」，交通頁寫「1 小時 55 分」，之後班表一改就更難對。
- 現在的事實表是一篇一份。禮文島主頁的研究有 126 筆事實，禮文島交通另有 102 筆，兩套編號各自獨立，同一班渡輪在兩邊是不同編號。大綱草稿引用的是主頁那套。
- 班表換季時，要知道哪幾頁用到了這個班次，現在沒辦法查。

### 解法：串接在大綱階段就決定，寫作時只照做

1. **分工表**：一件事只有一頁負責，其他頁一兩句帶過並連過去（已寫進規則）。大綱檢查程式擋下兩頁同時負責。
2. **每個地點一份共用事實表**：同一個地點的所有頁面用同一套事實編號。主頁的摘要句和交通頁的細節句，引用同一個編號，說法自然一致。班表改了，查一下哪些頁面用到這個編號，就知道要改哪幾頁。建議放在 `content-planning/<地區>/places/<地點>/facts.json`，每筆記下適用期間。
3. **內連表與連結句**：大綱就寫好「哪頁哪一節連到哪頁、這句連結是為了什麼」。寫作時照寫連結句；目標頁還沒上線就先不加連結，記進待補清單（已寫進規則）。目標頁上線後，程式只把那句話加上連結，字不改，所以不用重新驗收。
4. **寫作順序**：被最多頁連到的先寫，通常是交通頁與共用教學頁；地點條目最後寫，摘要才能對上已寫好的主題頁（已寫進選題規則）。
5. **固定的連結交給網站**：麵包屑、鄰近地點、出入口、適合月份，網站已經依地點欄位自動產生（`src/components/PlaceLinks.astro`），不用靠寫作。
6. **譯名表**：同一個地名、站名全站寫法一樣（`content-planning/glossary.json`）。
7. **群驗收**：一群的頁面全部上線後，派一個 agent 扮演要去這一帶的旅客，從主頁一路點完整群，只找頁面之間的問題：兩頁說法不同、連結斷掉、讀到一半不知道下一步去哪。這是現在的單篇驗收看不到的。

## 四、寫作內容怎麼保持可以調

你擔心交給 routine 之後就改不動。建議這樣設計：

- **意見放在正確的層**。規則分四層：全站規則（語氣、標題規範）、主題範本（交通頁、住宿頁的固定架構）、群大綱、單篇。你的意見寫進能涵蓋它的最高一層，之後的文章自動照新規則寫。這條已經是決定（「Darren 的意見寫進規則庫」）。
- **每篇記下用哪一版規則寫的**。驗收紀錄寫入當時 Skill 的 Git 版本。規則改了以後，程式列出「用舊規則寫的已上線文章」，依改動大小分三種處理：
  - 只影響標題：重跑標題檢查就好，便宜。
  - 影響架構或內容：排進低優先的重寫清單。
  - 只影響之後的文章：不動舊文章。
- **第一群當調整期**。稚內群大約 27 頁，預期這段時間規則還會一直改。建議等連續兩週沒有「要重寫已上線文章」的規則改動，再提高頻率。
- **抽查變成範例**。你抽查時的判斷（這段好、這段不行、為什麼）存成讀者驗收 agent 的校準範例，驗收會越來越接近你的標準。
- **隨時可以收回**。Sanity 可以把單篇改回不開放搜尋或取消發布；規則都在 Git，可以退回舊版；routine 可以隨時暫停。

## 五、讓你放心交出去的條件：分三段放手

| 階段 | routine 做到哪 | 你要做什麼 | 過關條件（建議） |
|---|---|---|---|
| A 試跑 | 寫到「驗收通過」，不發布 | 每篇都可以看，至少抽一半 | 連續 10 篇裡，8 篇以上一次或修一次就過；你抽查沒有找到驗收漏掉的事實錯誤；每輪都在時間內跑完；每篇成本有記錄 |
| B 發布但不開放搜尋 | 發布到 Sanity，維持 noindex，補內連 | 每週看摘要，抽 2～3 篇 | 一群全部上線，群驗收沒有擋路問題；連續兩週沒有要重寫已上線文章的規則改動 |
| C 全自動 | 自動開放搜尋 | 每週看摘要，每月抽查 | 你決定減少抽查 |

過關條件的數字都是暫定，由你決定。交接文件說「有 Sanity 之前先跑到驗收通過」，就是階段 A。

## 六、現在的設定建議先改的地方

1. **加停放狀態與輪數上限**：一篇最多兩輪（寫一次、修一次），不過就停放。目前規則沒有這條，退稿的文章會卡住清單。
2. **執行鎖逾時要比啟動間隔短**：現在鎖 12 小時才算過期，啟動間隔是 3 小時。有一輪中途當掉，後面約 4 輪都會空轉。建議改成比間隔短，並給每輪時間上限。
3. **頻率**：禮文島交通改了 6 輪才過，每輪動用約 8 個 agent（作者、4 個分段檢查、事實查核、讀者驗收、標題檢查），查核了 118 筆事實。每天 8 篇很可能撞到 Claude 的用量上限，而且用量和好材誌的 routine 共用。建議階段 A 每天 1～2 篇，量到每篇的實際時間和用量後再調。頻率由你決定，這次沒有改設定。
4. **清單驗證程式跟新流程對齊**：
   - 證據來源加入 `Google autocomplete`。
   - 頁型加入 `cross-place-page`。
   - 批次改成以旅行群為單位：一群跨好幾個地點，也就是好幾個 Hub，現在的規則是一批只能有一個 Hub。
   - 拿掉「一批頁數等於整份規格保留頁數」。
   - 文章清單要記錄停放狀態與「要回大綱」的原因。
5. **事實表改成每個地點一份**：先把禮文島主頁與交通頁兩套編號合併，大綱與之後的頁面都引用合併後的編號。
6. **分支合併**：routine 每次從 GitHub 重新下載 `main`。`plan/wakkanai-rishiri-rebun` 合併前，routine 看不到這些新規則。
7. **換行字元**：這台 Windows 會把檔案換行改成 Windows 格式，雲端是 Linux 格式。加一個 `.gitattributes` 固定成 Linux 格式，避免兩邊來回改出一大堆沒意義的差異。

## 七、工具清單與順序

對照交接文件第五節的第二、四階段，依「先讓串接成立，再接自動化」排序：

1. 地點共用事實表格式，合併禮文島兩套編號。
2. 自動完成研究工具（日文、中文）。
3. 地點關係格式與分群程式。
4. 主題範本：交通、住宿、步道、景點、天氣、美食、祭典。
5. 大綱格式（JSON）與大綱檢查程式。
6. 清單驗證程式改版（第六節第 4 點）。
7. 寫作與驗收改成照大綱寫：驗收加一項「H 樹與大綱一致、連結句都有寫」。
8. 待補內連清單與補內連程式。
9. 自動發布主流程：從好材誌搬過來，加入停放、輪數上限、時間上限、來源打不開的延後規則。
10. 群驗收 agent 的規則。
11. 事實適用期間與換季重查。
12. 每週摘要。

1～7 做完就可以用稚內群跑一次完整的規劃到驗收（交接文件第三階段）；8～12 在接上 Sanity 前完成。
