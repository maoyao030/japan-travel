# 日本旅遊長尾站潤稿

內容稿已經正確、完整，但讀起來像資料表被拆成句子。潤稿讓它像一位熟悉當地的編輯帶讀者排行程。**事實一個都不改，也不多加。**

2026-10-18 對照同題競品後的結論：僵硬的原因不在標點，在於什麼都交代、不排優先、不說後果、句子之間沒有因果。所以潤稿要做的不只是改句子，還要決定每段先講什麼。

## 五件事

1. **每段先給結論，替讀者排優先。** 段落開頭用一句說這段最重要的事（「排行程時，最需要先搞清楚的只有兩件事」），細節接在後面。一段塞了很多條件時，挑讀者最需要的一兩件講清楚，其他留給表格或後面的段落。不能刪掉內容稿的事實，可以移到同一段的後面。
2. **重要的事實接後果或建議。** 「末班船17:10」接「錯過末班船，當天就回不了稚內」。「清晨5點決定開不開」接「搭船當天早上記得先確認一次」。後果要能從事實直接推出來。
3. **用因果與轉折串起來。** 所以、如果、不過、反而、也因此。不要整段都是「A是B，C是D」。
4. **站在讀者的行程裡說。** 時刻表說「6:30開、17:10回」，編輯說「搭最早那班去、末班回，就能在禮文島待上一整天」。可以偶爾用「大家」「記得」直接對讀者說話。
5. **去掉照官網的句構。** 「依時刻表」「目前公布的…適用…」「必要時最多會…」改成自己的話。年份放在時刻表的標題或表格裡。

口吻與標點照寫作 Skill 的 `writing-guide.md`。不寫「官方沒寫」，不寫成本站去過。

## 能改與不能改

| 能改 | 不能改 |
|---|---|
| 段內句子的順序、合併或拆開 | 數字、時間、價格、日期 |
| 加從事實直接推出的後果與建議 | 日文原名、按鈕與招牌的日文 |
| 加轉折、因果與對讀者的提醒 | 事實編號（跟著它說明的句子走，放在句號前） |
| 刪掉同一段裡重複的說法 | 標題與層級、表格 |
| 換掉公文腔 | 大綱內連表的連結句，一字不改 |

### 推論的界線（上一輪潤稿多了24處意義改變，就是這裡出問題）

- **可以推的**：時刻表推出「錯過末班船當天回不了」「6:30的船要前一晚住稚內」，停航規則推出「當天早上先確認」。
- **不能推的**：
  - 營業時間沒寫的設施，不能建議「開船前在這裡吃飯」。
  - 不能推出「比較好」「比較划算」這種評價，除非事實裡有比較。
  - 「唯一」「只有」「一定」要有事實證明。例如利尻島有機場，就不能寫「唯一的方法是搭船」。
- **修飾詞照原文程度**：可能、原則上、約、建議、主要、一般，不能加，也不能拿掉。「導入」不寫成「加收」，「可能停航」不寫成「會停航」。
- **不能前後矛盾**：改完整段重讀一次。例如前一句寫「船上只有販賣機」，後一句就不能寫有小賣部。

## 範例

修改前（內容正確但僵硬）：

> 稚內到利尻島、禮文島的渡輪由Heartland Ferry（ハートランドフェリー）經營，從稚內港開往利尻島的鴛泊港和禮文島的香深港，兩島之間也有船互通。依2026年時刻表，夏季6月到9月稚內往兩島各有3個來回，1月到4月27日與11月到12月的冬季班表只剩2個來回。回稚內的末班船，香深出發夏季是17:10、其他季節17:05，鴛泊出發夏季與春秋是16:40、冬季17:30。颱風或低氣壓來時可能停航，原則上清晨5點到5點半決定當天開不開。

修改後：

> 從稚內前往利尻島或禮文島，就是搭Heartland Ferry（ハートランドフェリー）的渡輪。到利尻島的鴛泊港約1小時40分，到禮文島的香深港約1小時55分，兩座島之間也有船可以互搭。
>
> 排行程時，最需要先搞清楚的只有兩件事。第一是季節，夏天6月到9月稚內往兩島一天各有3個來回，冬天只剩2個，能選的船少很多。第二是回稚內的末班船。從禮文島香深出發，夏天最晚是17:10，其他季節是17:05。從利尻島鴛泊出發，夏天和春秋是16:40，冬天反而晚一點，是17:30。錯過末班船，當天就回不了稚內，只能在島上多住一晚。
>
> 天氣也會影響。颱風或低氣壓來時船可能停開，當天開不開，原則上清晨5點到5點半就會決定，所以搭船當天早上記得先確認一次。

改了什麼：
- 一段拆成三段，每段一個重點。
- 「最需要先搞清楚的只有兩件事」替讀者排優先。
- 末班船接後果，停航規則接建議。
- 「依2026年時刻表」拿掉，年份留在時刻表。
- 「可能」「原則上」「約」都保留，數字與日文名沒變。

完整的對照與競品分析見 `content-experiments/voice-study-2026-10-18/competitor-prose-study.md`。

## 流程

1. 讀內容稿的 `draft-tagged.md`、研究記錄的事實表，以及大綱裡這一頁的內連句。
2. 照上面的原則改寫，輸出新的 `draft-tagged.md`，另寫 `polish-notes.md` 列出所有新加的推論句。
3. 執行 `node .agents/skills/japan-travel-polish/scripts/check-polish.mjs <潤稿前> <潤稿後> --article=<articleId>`，直到通過。它比對數字、日文、事實編號、標題、表格與內連句。
4. 照寫作 Skill 重跑 `fact_tags.py`、`check-voice.mjs`、`audit_answer_first.py`。
5. **意義比對**：派一個沒參與潤稿的子代理，對照潤稿前後的 `reader-preview.md` 與事實表，逐段列出所有意義上的差異。把每一處分成三類：
   - 可以接受的推論（事實直接推得出來）
   - 不可接受（沒有事實撐、修飾詞改變、前後矛盾）
   - 刪掉了讀者需要的資訊
   
   潤稿者改掉後兩類，再重跑第 3、4 步。
6. 交給驗收。事實查核只需要重看新加的推論句與被改到的句子。

## 完成條件

`check-polish.mjs` 通過；`fact_tags.py`、`check-voice.mjs`、`audit_answer_first.py` 通過；意義比對沒有不可接受的差異；內連句原樣保留。
