# 日本旅遊長尾站潤稿

2026-10-18 比較了六種寫法（研究見 `content-experiments/polish-test-2026-10-18/ai-tone-study.md`），這一版在兩位評審的並排比較裡都排第一，在沒看過的利尻島交通頁也把「像AI的程度」從40～55降到20～30。正式流程的潤稿者用 Opus 5.5。

內容稿已經正確、完整，但讀起來像資料表被拆成句子，或像AI寫的。潤稿讓它像一位熟悉當地的台灣旅遊編輯，在跟朋友解釋怎麼排。**事實一個都不改，也不多加。**

## 先讀這段：什麼叫AI腔

2026-10-18 量了9篇台灣旅遊文章（Funliday、好運日本行、JeePe、個人部落格），和我們潤過的稿比，差別很明顯（每千字次數，真人最大值／我們潤過的稿）：

| 用字 | 真人 | 我們 | 為什麼像AI |
|---|---|---|---|
| 所以 | 0.4 | 2.3 | 每個事實都用「所以」接後果，像推理題 |
| 記得 | 0.8 | 1.3 | 每段都在提醒 |
| …的人 | 0.8 | 4.0 | 「帶腳踏車的人要」「想升等的人」，像在分類讀者 |
| 要 | 3.9 | 8.6 | 指令語氣，換成「得」也一樣 |
| 和 | 2.7 | 6.3 | 每個並列都用「和」，真人多用頓號與「與」 |
| 約 | 2.8 | 9.0 | 每個數字都「約」 |
| 逗號 | 37 | 44 | 短句用逗號一路接下去，像條文 |

另外有一類句型，真人9篇、4.7萬字裡合計只出現6次，我們一篇就有16次。它們都是**在講內容之前先宣布內容**：

- 「最先要搞清楚的是兩件事。第一是季節…第二是…」
- 「關鍵是開船前24小時這條線」「島間船是串起兩島的關鍵」
- 「電話預約還有一個好處」「開放日還有一個小例外」
- 「三個渡輪站的樓層安排有個共通點」
- 「票價方面，」「要記住的是這幾個時間點」「各個時間點依序是：」
- 「上一節提到」「晚於上面時間點清單的截止時間」

人講話時直接講那件事。重要的事放前面，讀者自然知道它重要，不用宣布。`check-voice.mjs --final` 會擋這些句型；用字頻率只印「提醒」，看提醒找出要整句改寫的地方，**不要用換同義詞過關**（把「要」換成「得」、「和」全換成「與」，評審一樣看得出來）。

盲測評審還抓到三種破綻，程式抓不到，要自己注意：

- **名詞標籤開頭**：「網路預約在渡輪公司的WEB予約頁」「特別室每段每組另收20,000日圓」，像條列標題改寫成句子。
- **寫出查資料的過程**：「在樓層圖上標示為」「渡輪公司公布的天數分別是」。讀者不需要知道資料從哪張圖來。
- **一個動作一句**：「第一次使用先註冊會員。日文畫面的姓名欄填全形平假名。手機切到日文鍵盤…」，像操作手冊逐條切開。

## 怎麼改

1. **重要的放前面，直接講。** 每段第一句就是內容本身：「6月到9月一天有3個來回，冬天只剩2個」，不是「首先要看季節」。
2. **句子從讀者想做的事開始。** 「網路預約在WEB予約頁」改成「想在網路上訂，到渡輪公司的WEB予約頁」。「特別室每段每組另收20,000日圓」改成「一群人想包一間的話，可以訂特別室，每段每組另收20,000日圓」。
3. **連續的動作串成一句話。** 用「再」「然後」「接著」「只不過」「不然」把同一件事的步驟接起來，不同的事才用句號分開。
4. **事實接後果，但換著接。** 末班船接「錯過了，當天就沒有船回稚內」。後果可以直接接在逗號後、寫成條件句「…的話，…」，或放到句首。整篇的「所以」不超過兩三次。句子因此太長、逗號太多時，把後果拆成下一句。
5. **少下指令。** 規定照寫（「手續要在開船40分鐘前辦好」），提醒不要每句都「要…」「記得…」「得…」。改成「最好」「可以」，或只寫後果讓讀者自己判斷。**但原文是必須做的事（不做會被收費、會被取消），不能從「要」改成「可以」。**
6. **對讀者說，不分類讀者。** 「帶腳踏車的人要早點到」改成「帶腳踏車的話，早點到比較好」或「如果帶腳踏車，…」。可以偶爾用「大家」。
7. **替讀者選一個預設，但條件要寫出來。** 「不在意坐哪裡的話，2等就夠了，上船自己找位子」可以，因為條件和理由都是事實。沒有條件的「最推薦」「最方便」不行。牽涉划不划算時，門檻要用事實裡的數字算出來並寫進句子：一日券2,500日圓、繞島一圈單程合計2,550日圓，就寫「繞島一圈以上才划算」，不寫「想多坐幾段就買一日券」。
8. **把時刻表講成行程。** 班次少的地方，用一兩句說一天怎麼走：「想在禮文島玩一整天，夏天搭最早6:30那班去、17:10那班回」。只能用時刻表上的班次，不算能待幾分鐘。
9. **同一件事只講一次。** 內容稿常在好幾節重複同一件事（例如QR code上船、1等可以選位、2等也能網路訂）。開頭兩段的概述可以和正文重複；其他重複留在最需要它的那一節講清楚，其他地方刪掉或一句帶過，刪之前確認那一節還有讀者要的時間與條件。可以跨節刪重複，`check-polish.mjs` 會列出來給意義比對確認，但整篇的數字、日文與事實編號都要還在。
10. **日文官網用語換成台灣說法。** 招牌與按鈕上的日文照寫，敘述用台灣說法。譯名以 `content-planning/glossary.json` 為準，那裡沒有的照下表。
11. **節奏有長有短。** 偶爾一句很短的話（「船上沒有餐廳。」）比一路長句自然。不要每段都用建議收尾。

## 能改與不能改

| 能改 | 不能改 |
|---|---|
| 句子的順序、合併或拆開 | 數字、時間、價格、日期 |
| 加從事實直接推出的後果與建議 | 日文原名、按鈕與招牌的日文 |
| 換掉AI腔、公文腔與指令語氣 | 事實編號（跟著它說明的句子走，放在句號前） |
| 刪掉重複的說法，包括跨節的重複 | 標題與層級、表格 |
| | 大綱內連表的連結句，一字不改 |

### 推論的界線

- **可以推的**：時刻表推出「錯過末班船當天回不了」，停航規則推出「當天早上出門前查一次」，「不在意座位的話2等就夠」（2等不對號是事實），「帶腳踏車的話早點到比較好」（不能預約、先到先上是事實）。像這樣**理由就寫在同一句、而且是事實**的輕微建議可以用「比較好」「就好」。
- **不能推的**：
  - 營業時間沒寫的設施，不能建議「開船前在這裡吃飯」。
  - 兩個選項之間的「比較好」「比較划算」「最方便」，要有事實比較兩邊。
  - 「唯一」「只有」「一定」「就知道」要有事實證明。利尻島有機場，就不能寫「唯一的方法是搭船」；天氣急變也可能臨時停航，就不能寫「早上查一下就知道」。
  - 「很多」「不少」要有數字撐。3個來回變2個是「少一個來回」，不是「少很多」。
- **修飾詞與範圍照原文**：可能、原則上、約、建議、主要、一般、要、只、都、每天、在這一帶，不能加，也不能拿掉。「在這一帶有三段航線」不寫成「有三段航線」（還有奧尻航線），營業時間沒寫全年無休就不加「每天」。「可能停航」不寫成「會停航」，「要在開船前取消」不寫成「可以在開船前取消」。「約」和「左右」「大約」程度一樣，可以互換。
- **用詞前後一致**：同一篇裡「帶車」指汽車，就不要拿來指腳踏車。
- **不能前後矛盾**：改完整段重讀一次。例如寫了「船上只有販賣機」，後面就不能有小賣部；要寫成「船上沒有餐廳，有飲料和冰淇淋販賣機，5月到10月另有小賣部」。

## 流程

1. 讀內容稿的 `draft-tagged.md`、研究記錄的事實表，以及大綱裡這一頁的內連句。
1-1. **先讀好運日本行與 MATCHA 的同類文章**（Darren 2026-10-19 指定的口吻目標）。照 `references/style-sources.md` 依段落功能挑三到五篇，用 `curl` 或瀏覽器讀到暫存區（不進 repo），歸納他們怎麼開段、怎麼推薦、怎麼講步驟、怎麼帶讀者看日文、怎麼講費用，用自己的話寫進 `polish-notes.md`。改每一節前，先讀一次功能相同的參考段落，再照那種講法寫我們的事實。只學講法，不抄句子，不學他們的事實。2026-10-19 試驗：同一篇渡輪頁多這一步後，兩位評審的怪句從 24～42 條降到 10～13 條，像好運日本行／MATCHA 的程度從 42～45 升到 70～74。
2. 照上面的原則改寫，輸出新的 `draft-tagged.md`，另寫 `polish-notes.md` 列出所有新加的推論句與跨節刪掉的重複。`reader-preview.md` 不用自己寫，第4步的 `fact_tags.py` 通過時會從 `draft-tagged.md` 拿掉事實編號自動產生。
3. 執行 `node .agents/skills/japan-travel-polish/scripts/check-polish.mjs <潤稿前> <潤稿後> --article=<articleId>`，直到通過。它比對整篇的數字、日文、事實編號，以及標題、表格與內連句，並列出跨節刪掉或搬動的內容。
4. 照寫作 Skill 重跑 `fact_tags.py <資料夾>`、`audit_answer_first.py <reader-preview.md> --article-type <頁型> --reference-review <研究記錄>`，以及 **`check-voice.mjs --final <reader-preview.md>`**（AI腔句型照擋，用字頻率只提醒），再跑 `node .agents/skills/japan-travel-polish/scripts/check-copy.mjs <reader-preview.md> <第1-1步讀下來的每一篇.txt>` 確認沒有照抄。檢查與「事實接後果」「動作串成一句」衝突時，順序是事實、讀者用得上、自然，最後才是檢查數字。
4-1. 通過後自己從頭讀一次，用「先讀這段」裡程式抓不到的三種破綻逐段自查再改。
4-2. **編輯挑錯→修一輪**：派一個沒參與潤稿的子代理，照 `agents/editor-review.md` 當台灣資深旅遊編輯，逐句挑出不像台灣人講的話（翻譯腔、公文腔、AI腔、重複、語意不通）並給改法。潤稿者逐條處理，寫進 `polish-notes.md`：照方向改，但編輯的改法會改到事實、加了事實沒有的操作建議、或要動標題與內連句時，以事實與本 Skill 為準，不同意的寫理由。改完重跑第 3、4 步。2026-10-18 試驗：多這一輪後兩位評審都判勝出（像AI的程度 45→30），但編輯的建議也帶進新的意義改變，所以後面一定要接意義比對。只修一輪，多輪會累積意義漂移。
5. **意義比對**：派一個沒參與潤稿的子代理，對照潤稿前後的 `reader-preview.md` 與事實表，逐段列出所有意義上的差異，分成三類：
   - 可以接受的推論（事實直接推得出來）
   - 不可接受（沒有事實撐、修飾詞改變、前後矛盾）
   - 刪掉了讀者需要的資訊（跨節刪重複時，確認讀者在需要的那一節還找得到）

   潤稿者改掉後兩類，再重跑第 3、4 步。
6. 交給驗收。事實查核只需要重看新加的推論句與被改到的句子。

## 完成條件

`check-polish.mjs` 通過；`fact_tags.py`、`audit_answer_first.py`、`check-voice.mjs --final` 通過；`check-copy.mjs <reader-preview.md> <讀過的參考文章.txt…>` 通過（沒有和參考文章連續相同 12 字以上的片段）；意義比對沒有不可接受的差異；內連句原樣保留。
